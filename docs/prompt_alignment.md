# Prompt Hash Alignment Guide

**⚠️ REQUIRED READING for anyone modifying `local_runner/prompt.py` or the Kaggle evaluation notebooks.**

YentlBench relies on a strict string-matching mechanism to link predictions from different model runs together. This document explains how that mechanism works, why it was designed this way, and how to avoid silently breaking your benchmark merges.

## The Mechanism: Outer Joins via SHA-256

When `yentlbench merge` reads multiple `.run.json` artifacts, it needs a way to confidently say: *"The clinical case evaluated in Run A is the exact same clinical case evaluated in Run B."*

Because Kaggle's evaluation harnesses do not easily pass through custom metadata like `stay_id` or `quintet_id` into the final nested JSON logs, `merge_runs.py` relies on the **prompt text itself** as the primary key.

Specifically, it computes a 16-character SHA-256 hash of the normalized prompt string (`prompt_hash`). It then performs a Pandas `outer join` across all runs using this hash. If two runs evaluated the exact same clinical case, their hashes will match perfectly, and their predictions will align horizontally in the same row of `merged_evaluations.csv`.

## The "Chief complaint:" Normalization Step

To accurately compare predictions across different demographic variants (e.g., `male` vs `female`), the prompt hash must capture the *clinical* information but ignore the *demographic* information.

To solve this, `merge_runs.py` applies a `normalize_prompt(text)` function before hashing. This function finds the string `"Chief complaint:"` and **strips away everything that comes before it**.

In our prompt template, demographic information (Name, Sex, Pronouns) is injected *above* the `"Chief complaint:"` line. By stripping this prefix, the resulting hash perfectly isolates the clinical core (complaint, vitals, pain) which is absolutely identical across all 5 quintet variants.

## The Silent Failure Mode (NaN Fragmentation)

Because of this strict hashing mechanism, **even a single invisible character difference** between two prompts will produce entirely different SHA-256 hashes.

If the prompt generated by the Kaggle notebook has a trailing space that the `local_runner` lacks, or if one uses `\r\n` while the other uses `\n`, their hashes will diverge.

**What happens when hashes diverge?**
The merge step will not throw an error. Instead, the Pandas outer join will create two distinct rows instead of one. 
- Row 1 will have Kaggle's prediction, but `NaN` for the local runner's prediction.
- Row 2 will have `NaN` for Kaggle's prediction, but the local runner's prediction.

This silent fragmentation destroys the pairwise comparisons later in the pipeline, as the analysis scripts cannot compute differences between models or variants if they aren't perfectly aligned on the same row.

## Verification Checklist for New Variants

If you modify `local_runner/prompt.py` or update the Kaggle evaluation harness, you **must** verify that your changes do not break hash alignment.

Before trusting your runs, verify the following:

1. **Exact Character Matching:** Print the generated prompts from both environments and assert absolute string equality.
2. **The `Chief complaint:` Anchor:** Ensure your new prompt still includes the exact literal string `"Chief complaint:"`. If you change this to `"Complaint:"`, the normalization step will fail, and demographic variables will leak into the hash, breaking the join.
3. **Run a Merge Test:**
   Run `yentlbench merge` on a small sample of your new outputs. Check the terminal output or the `merged_evaluations.csv`:
   - If the merged table shape has exactly as many rows as your source dataset (e.g., 70), alignment succeeded.
   - If the merged table shape has $2\times$, $3\times$, or $4\times$ as many rows as your source dataset, your hashes are misaligned and the outer join has fragmented your data. Look for columns entirely filled with `NaN`s on certain rows.
