# Kaggle vs. Local Runner Workflow

YentlBench is designed to evaluate clinical bias across a wide spectrum of Large Language Models. To support both proprietary APIs and local open-weights models, the framework utilizes a dual-track execution strategy that converges on a single unified artifact format.

## Two Execution Tracks

### 1. Kaggle (Frontier Models)
State-of-the-art proprietary models (like GPT-4o, Claude 3.5, and Gemini 1.5) are evaluated via Kaggle notebooks. This track is preferred for API-based models to manage secrets securely, utilize cloud concurrency, and produce reproducible evaluation artifacts. 
- These runs generate `*.run.json` files containing the prompts, predictions, and metrics.

### 2. Local Runner (Local Models)
Local open-weights models (like Llama 3, Mistral, and Qwen) are evaluated on your local machine using Ollama. This is orchestrated entirely by the CLI:
```bash
yentlbench run --model llama3:8b --variants female male
```
- Just like the Kaggle notebooks, the local runner produces identically structured `*.run.json` files. 
- Contract tests ensure strict schema compatibility between Kaggle outputs and local outputs.

## Mixing Results

Because both tracks produce the exact same `.run.json` schema, the `yentlbench merge` command treats them identically. 

To mix results from both sources into a single benchmark analysis:
1. Download the `.run.json` artifacts from your Kaggle notebook runs.
2. Place the Kaggle artifacts into your designated results directory (e.g., `results/`).
3. Run your local models using the CLI, pointing the output to the same directory:
   ```bash
   yentlbench run --model llama3:8b --results-dir results/
   ```
4. Merge all runs together into one comprehensive CSV:
   ```bash
   yentlbench merge --results-dir results/ --output eval/merged_evaluations.csv
   ```

The resulting `merged_evaluations.csv` will contain predictions side-by-side from both local and cloud models.

## The Filename Convention (And Why It Matters)

`yentlbench merge` does **not** rely on complex metadata inside the JSON file to determine what model or demographic variant it is looking at. Instead, it parses the filename. 

Both Kaggle and the local runner strictly adhere to the following naming convention:
```
batch_esi_triage_scorer_{variant}-run_id_Run_{run_number}_{model_slug}.run.json
```

**Examples:**
- `batch_esi_triage_scorer_female-run_id_Run_1_openai_gpt-4o.run.json`
- `batch_esi_triage_scorer_nb_ambiguous-run_id_Run_1_llama3_8b.run.json`

**Why it matters:** The merge script applies a regular expression to extract the `variant` and the `model_slug` directly from the file name. It uses these to create the unique column suffixes in the final CSV (e.g., `predicted_score__female__llama3_8b`). If you rename these files arbitrarily, the merge step will fail or group the data incorrectly.

## Prompt Hash Alignment

To merge predictions from multiple models into a single tidy dataframe, `yentlbench merge` performs an outer join using the **SHA-256 hash of the prompt text**.

This means that the prompt generated by the Kaggle track and the prompt generated by the local track **must be identical down to the last character**. If a local prompt has an extra trailing space or a different newline character compared to the Kaggle prompt, their hashes will diverge, and the merge script will treat them as two entirely different clinical cases, creating missing data (NaNs) in your merged CSV.

For detailed instructions on how to ensure absolute prompt consistency between the two environments, please read [prompt_alignment.md](prompt_alignment.md).
